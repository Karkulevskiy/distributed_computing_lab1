# Задание 1
Для компиляции программы используйте команду `gcc main.c -o mandelbrot -fopenmp -lm`

Затем программа запускается командой `./mandelbrot nthreads npoints`

### Алгоритм

После запуска программа равномерно распределяет точки по заданной области(область задаётся константами в main.c) и каждую из точек проверяет на условие вхождения в множество Мандельброта. Условие проверяется по следующему алгоритму:

 1. Запускаем цикл от 0 до MAX_ITER(указывается в main.c), Z изначально равно 0, С - наша точка
 2. В каждой итерации обновляем Z по формуле Z = Z^2 + C
 3. После всех итераций, проверяем, если модуль нашей точки Z ушёл за пределы двух(|Z|>2), то эта точка не принадлежит множеству Мандельброта

 После нахождения точек они записываются в файл [mandelbrot_points.csv](https://github.com/Karkulevskiy/distributed_computing_labs/blob/lab2/task1/mandelbrot_points.csv), а также в файле [mandelbrot_visualization.txt](https://github.com/Karkulevskiy/distributed_computing_labs/blob/lab2/task1/mandelbrot_visualization.txt) отрисовывается визуализация всех найденных точек на координатных осях X и Y

## Выводы по производительности

- По графикам видно, что при увеличении числа потоков от 1 до ~ncores(количество ядер на процессоре) производительность растёт, что особенно заметно при большом количестве точек 

- При количестве потоков, значительно превышающем количество ядер(в нашем случае 32 и выше) производительность значительно падает из-за частых переключений контекста и нагрузки на планировщик ОС

- При большем числе точек можно использовать большее количество потоков. Таким образом при 2500 точек оптимальное число потоков - 8(ускорение программы в **~1.8x** по сравнению с 1 потоком, время выполнения: **0.00196 сек**). При 50000 точек оптимальное число потоков - 16(ускорение программы в **~5.2x** по сравнению с 1 потоком, время выполнения: **0.015 сек**)

# Задание 2

### Тестовые данные
Данные генерировались с помощью скрипта `data_generator.py` для следующих размеров:
- 100 частиц
- 300 частиц  
- 500 частиц
- 700 частиц
- 1000 частиц

Каждая частица содержит: массу 1e9-1e12 кг, координаты ±100 единиц и скорость ±2 ед/сек.

### Параметры симуляции
- **Общее время**: 5.0 секунд
- **Шаг интегрирования**: 0.001 секунды
- **Количество шагов**: 5000

### Конфигурация тестов
*OpenMP* тестировалось с 1, 2, 4 и 8 потоками

*CUDA* тестировалось с размером блоков 256
  
Пример тестовых данных лежит в `task2/data`.
Пример результатов вычисления координат точек лежит в `task2/results`.

## Выводы по производительности

- CUDA значительно быстрее OpenMP - при 1000 частиц ускорение достигает 100 раз относительно 1 потока и 35 раз относительно 8 потоков OpenMP.

- OpenMP масштабируется с потоками - время выполнения сокращается при увеличении числа потоков, но не линейно.

- CUDA показывает почти постоянное время - время выполнения слабо зависит от количества частиц благодаря параллельной архитектуре GPU.

- При малых данных разница меньше - для 100 частиц CUDA лишь в 2 раза быстрее OpenMP с 8 потоками.

- Оптимальный выбор зависит от размера задачи:

  - Малые задачи (до 300 частиц) - OpenMP применим, но CUDA всё равно производительнее

  -  Средние и крупные задачи (500+ частиц) - CUDA существенно эффективнее

# Задание 3
### Read-heavy сценарий:
- Стандартный pthread_rwlock_t показывает стабильное увеличение производительности с ростом потоков до 8 и плавное падение дальше.
- Кастомная реализация работает почти одинаково на 1-2 потоках, но значительно теряет производительность при увеличении числа потоков (особенно при 8+ потоках), из-за блокировки всех новых read при присутствии write.
<img width="721" height="547" alt="1" src="https://github.com/user-attachments/assets/16f90199-9841-471a-886c-8b7b3b7f341e" />

### Balanced сценарий:
- Производительность обеих реализаций падает с увеличением числа потоков, так как количество операций записи существенно больше и возникает конкуренция.
- Пользовательский rwlock демонстрирует большее падение при больших потоках.
<img width="713" height="547" alt="2" src="https://github.com/user-attachments/assets/45772544-7b44-4a7a-85b5-c9d78ce6306b" />

### Write-heavy сценарий:
- Производительность сильно ограничена количеством write.
- Кастомная реализация хуже стандартной, особенно при 16 и 32 потоках.
<img width="713" height="547" alt="3" src="https://github.com/user-attachments/assets/91510825-bb77-4263-ad8a-27bfaf4c44c0" />

## Вывод по производительности
- На низком числе потоков (1-2) кастомная реализация сравнима со стандартной.
- При высоком числе потоков (>8) стандартный pthread_rwlock_t значительно эффективнее.
- Используемая политика приоритета write блокирует новых read, создавая узкое место при большом количестве потоков.
- Возможны расходы на частое пробуждение потоков через pthread_cond_signal/broadcast.
